## 背景：為什麼「沒檢查 isEnabled」是一整類 bug

`Myau.java` 在啟動時對 **每一個** 模組呼叫 `EventManager.register(module)`，
不管有沒有開。所以每個 `@EventTarget` 都會一直被呼叫，模組必須自己檢查
`isEnabled()`。漏掉的話，模組「關著」也在運作。

## 🔴 嚴重

### 1. ✅ Blink 的逐步釋放從來沒有真的釋放過
`Blink.drain()` → `PacketUtil.sendPacketNoEvent()` → `sendPacket(p, null)`
（varargs 版，SRG `func_179288_a`）→ `MixinNetworkManager.sendPacket2`
→ 此時 `blinking == true` → `BlinkManager.offerPacket()` 又把封包收回佇列尾端。

- 佇列不會變短，只會被「輪轉」（順序被打亂）。
- 佇列裡如果沒有 C03，`while (allowance > 0)` 永遠不會結束 → **client 凍結**。
- 釋放實際上只會在 `release-on-correction` 收到 S08、清空佇列時結束。

**證據（log）：**
- `2026-09-20-3.log.gz`：`released on packet limit (0.0 blocks, 78 → 368 → 1221 → 293 packets)`
  — 佇列一直在長。
- `2026-09-22-2.log.gz 20:47:59`：Blink released → 20:48:00 `LAGBACK x6 … BLINKx10`
  → Blink OFF。是被伺服器修正關掉的，不是 drain 自己跑完。
- 用 `javap` 確認過安裝中的 jar：`sendPacketNoEvent` 呼叫的是
  `func_179288_a`，refmap 裡 `sendPacket2` 也掛在這個方法上。

**修法：** `BlinkManager.release(Packet)` — 送出時設 `releasing` 旗標，
`offerPacket` 看到旗標就不收。LagManager 仍然看得到這個封包（維持原本的組合行為）。

> 注意：修好之後，`release-per-tick = 2` 的意思變成「每 tick 真的送出 2 個 C03、
> 同時進來 1 個」，也就是淨清空速度 1/tick。這仍然違反 ENGINEERING-NOTES §1
> 的定律（一個 tick 送兩個位置封包），只是現在「會結束」。如果要照 §1，
> 應該改成「丟掉路徑、只送終點」。📝 待你決定。

### 2. ✅ TimerRange 完全沒有 `isEnabled()` 檢查
`onTick`、`onAttack`、`onPacket`、`onRender3D` 關閉時都在跑：
- 預設 MODERN 模式：往前走、看著附近的玩家一段時間後，**模組關著也會把 timer 拉到 1.5 倍**。
- `shouldResetTimer()` 會一直把 timer 設回 1，蓋掉 Timer／Scaffold。
- `blink` 選項開著時，關閉狀態也會攔截收到的封包。

**修法：** 四個 handler 都加上 `isEnabled()`。

### 3. ✅ Ambience 關閉時仍然控制世界時間
關閉時仍會取消 `S03PacketTimeUpdate`，並在每一幀把時間設成 `Time` 的值（預設 0）。

**修法：** 三個 handler 都加上 `isEnabled()`。

## 🟠 高

### 4. ✅ KillAura smooth-back 會跳過清理
LB 轉頭模式（rotations==4）＋ `smoothBack` 時，`onDisabled()` 會 `setEnabled(true)`
然後 `return`，跳過了：
- `setBlinkState(false, AUTO_BLOCK)` → 轉回來的整段時間都還在扣移動封包；
- `isBlocking`／`fakeBlockState` 重設；
- 待處理的 `blinkReset` → 模組關掉後又把 blink 開起來。

**修法：** 清理移到 smooth-back 分支之前，並清掉 `blinkReset`。

📝 未修：smooth-back 期間 `isEnabled()` 是 true，所以 Panic 會回報「已停止」，
但 KillAura 其實還開著幾個 tick。如果這時關遊戲，config 會存成開啟。

### 5. ✅ 設定檔裡 KillAura 是開的 → 啟動時 NPE → 設定檔只載入一半
`Config.load()` 在遊戲啟動時（還沒有玩家）就呼叫 `setEnabled(true)`，
`KillAura.onEnabled()` 用了 `mc.thePlayer.rotationYaw` → NPE，
被最外層 `catch (Exception)` 接住 → **迴圈中斷，後面的模組全部維持預設值**。

**修法：**
- `Config.load()`：每個模組的 `setEnabled` 各自 try/catch，並寫進 log。
- `KillAura.onEnabled()` 加上 null 檢查（`onTick` 會在有玩家後重新取得轉頭角度）。
- `Fly.onDisabled()` 同樣加了 null 檢查。

### 6. ✅ FakeLag 把傳送確認封包丟掉（信心：中）
S08 進來（netty 執行緒）→ `flushRequested = true` → 主執行緒處理 S08 並回一個 C06
→ C06 是 C03 子類，被扣住 → 同一個 tick POST 的 `discardStalePositions()`
把它和舊位置一起丟掉。

**修法：** `flushRequested` 期間遇到 C06 時，立刻丟掉舊位置，並讓 C06 直接送出。

### 7. 📝 LagManager 會扣住 `C0FPacketConfirmTransaction`
`LagManager.handlePacket` 沒有排除 C0F，也不檢查執行緒。這和 NOTES §2
「Never delay C0F」衝突。但 LagRange 目前實際上能用、沒有被踢，所以沒有改。
**建議：** 用 FlagDetector 或 ServerFingerprint 看 LagRange 開著時有沒有
pong 相關的斷線，再決定。

## 第二輪：你回報的兩個症狀

### 「Blink 會回溯」
主因就是 #1。drain 從來沒有把路徑送出去，伺服器一直停在 anchor，
最後由伺服器的修正（S08）結束這一輪 → client 被拉回 anchor ＝ 回溯。
log 裡的 `released → LAGBACK … BLINKx10 → OFF` 就是這個順序。

另外兩個會造成回溯的路徑：
- **關掉 Scaffold 會倒掉 Blink 的佇列**：`Scaffold.onDisabled()` 呼叫
  `setBlinkState(false, BLINK)`，不管 Scaffold 自己有沒有在 blink。
  ✅ 已改成 `BlinkModules.SCAFFOLD`。
- 📝 **按鍵關閉 Blink** 仍然是一個 tick 送出整個佇列（NOTES §1）。drift 小
  （1–3 格）時伺服器通常會接受，`max-drift` 仍然是真正的控制桿。

附帶影響：Scaffold 的 safe-stuck 以前是用 `BLINK` 的名字記進 ActionLedger，
所以**舊 flag 檔裡的 `BLINKx` 有一部分其實是 Scaffold**。

### 「FakeLag 直接卡住，動不了」
從反編譯的 1.8.9 `NetHandlerPlayServer` 確認的伺服器行為：

1. 伺服器傳送你（`setPlayerLocation`）時會設 `hasMoved = false`。
2. `hasMoved == false` 的時候，**伺服器忽略所有移動封包**，直到收到一個離傳送點
   0.5 格以內（`d3 < 0.25`）的位置封包。
3. `hasMoved == false` 的時候，**所有放方塊都會被拒絕**
   （`processPlayerBlockPlacement`：`if (this.hasMoved && …)`）。

vanilla client 收到 S08 後會馬上回一個剛好在傳送點的 C06，
這就是解除 `hasMoved == false` 的那個封包。FakeLag 以前會把它扣住再丟掉（#6），
所以伺服器一直停在「忽略你的移動」的狀態 ＝ 動不了。

**證據：** `flags-20260920-222005.txt` 22:20:14 連續 5 次 REJECT，
最近的對手在 18–20 格外（`body 18.54 … 20.54`），全部 `FakeLagx106–110`。
附近沒有人擋著，放方塊卻一直被拒絕，符合第 3 點。
另外還有 `LAGBACK x21 in 0.3s`、`x15 in 1.55s` 這種連續修正，符合 NOTES §2
「修正會自我放大」。

✅ #6 的修法（讓 C06 直接送出）第二輪又補了一點：處理完之後把 `flushRequested`
清掉，tick 就不會再丟一次 C06 之後的新位置。

**信心：** 這個機制本身是確定的（伺服器原始碼），但 FakeLag 卡住是不是
「只有」這個原因，要實測才知道。NOTES §5 把 FakeLag 標成放棄了，
可以用一場測試看它現在是否可用。

### 實測結果（2026-09-23 19:15，BedFight，`flags-20260923-191559.txt`）
設定：DYNAMIC、delay 200、release-on-attack 開、max-held 40，ping 180–220ms。

- 9 秒內 31 次修正，**7 筆全部在打人後 1–4t 或被擊退後 1–7t**，開賽前一筆都沒有。
- 最大的一筆：`LAGBACK x13 in 0.6s`。以前的場次是 `x21 in 1.0s`、`x15 in 1.55s`，程度差不多，
  所以不是這次的修改造成的。
- `TIMER-ORPHAN`／`DRAIN-STALL` 都沒觸發。
- 症狀從「卡住動不了」變成「一直被 flag」，但這場太短，沒辦法確認卡住已經完全修好。

**結論：** 和 NOTES §5 放棄 FakeLag 的原因一樣。兩個觸發點都是設計本身的問題：
1. 被擊退後位置還被扣著 → 伺服器等不到你照擊退移動 → 拉回。
2. `release-on-attack` 把扣住的位置壓縮成一次送出 → 違反 §1。

使用者已經關閉 FakeLag，維持關閉。

### 第三輪：參考 LiquidBounce 新增 `LIQUID` 模式
讀了 LiquidBounce 的 legacy `combat/FakeLag.kt`（1.8.9）和 nextgen
`ModuleFakeLag.kt`。最大的差別：**LiquidBounce 只在接近敵人時扣，
一開始交手就全部放掉，之後冷卻一段時間不扣**；我們原本的 DYNAMIC 剛好相反，
扣封包的時間集中在交手的時候。

新模式 `LIQUID`（原本三個模式不動，設定檔不受影響）：

| 條件 | 行為 | 來源 |
|---|---|---|
| 敵人離伺服器端位置 ≤ `melee-distance`（3.5） | 全部放掉，並開始 recoil | legacy MinAllowedDistToEnemy |
| 伺服器端位置比真實位置更靠近敵人（在後退） | 不扣 | nextgen |
| 自己的 S12 擊退、爆炸擊退、S06 扣血 | 立刻照順序全部放掉（排程到 client thread）＋ recoil | 兩版都有 |
| 打人（`release-on-attack`） | 攻擊直接送出，前面扣的照順序放掉 ＋ recoil | legacy BlinkOnAction |
| 放方塊、挖掘、換手持、疾跑切換 | 照順序放掉 ＋ recoil | 兩版都有 |
| 沒在移動、用物品、開畫面、在水裡、受傷中、單人模式 | 不扣（不觸發 recoil） | legacy／nextgen |
| S08 | **維持我們的做法**：丟棄舊位置、C06 直接送出 | 刻意不照抄（legacy 會把舊位置送出去，違反 §2） |

新設定：`melee-distance`（3.5）、`recoil-time`（750ms），只在 LIQUID 模式顯示。
放掉的方式是「全部照順序送出」（和 LiquidBounce 一樣），**不是**壓縮成最後一個位置。
一個 tick 送出多個位置仍然違反 §1，但 recoil 讓它很少發生。

**建議測試設定：** `mode LIQUID`、`delay` 先用 200（LiquidBounce 預設 550 是給低延遲用的）、
`range` 8、`melee-distance` 3.5、`recoil-time` 750。
**要看的：** flag 還會不會集中在「打人後 1t／被擊退後」。如果 LIQUID 有效，
戰鬥中的 flag 應該大幅減少，flag 反而會出現在接近敵人、第一次放掉的那一刻。
